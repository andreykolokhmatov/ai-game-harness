# AI Game Development Harness — план v2

## Что меняется по сравнению с исходным планом

1. **Проверка игры — ядро системы.** Каждая игра с первого дня создаётся из шаблона с встроенным debug-слоем, чтобы её можно было тестировать программно, а не только мнением модели.
2. **Web-экспорт проверяется с первого прототипа**, а не в конце: Yandex Games — это браузер.
3. **Меньше ролей.** Skeptic, QA и Evaluator объединены в один слой оценки; Final Auditor — в основном детерминированный чеклист.
4. **Ассеты — отдельная стратегия**, а не побочная задача Engineer.
5. **Решение человека после прототипа** (можно отключить в конфиге).
6. **Состояние — журнал событий** вместо набора JSON-файлов.
7. **Состояние Harness хранится вне Git-репозитория игры**, чтобы откат игры не стирал историю самого отката.

## Принципы

- Harness — оркестратор. Код пишет Claude Code.
- Истину о работе игры определяют инструменты (Godot, Playwright, тесты). LLM интерпретирует их результаты.
- Тот, кто сделал работу, её не принимает. Оценщик запускается в чистом контексте и ничего не исправляет.
- Каждый этап заканчивается проверяемым критерием «готово».
- Любой цикл ограничен по итерациям, времени и бюджету.
- Всё, что специфично для Yandex, лежит в отдельном слое с источниками.

## Роли

| Роль | Что делает | Модель по умолчанию* |
|---|---|---|
| **Planner** | Идея → GDD, затем техническая архитектура и план задач. Analyst и Architect объединены на старте; разделяются, если понадобится | Opus 5.5, high |
| **Engineer** | Реализует задачи в проекте, запускает Godot и тесты | Sonnet 5.5, medium |
| **Evaluator** | Запускает проверки, анализирует отчёты, скриншоты и логи, ищет поломки. Выдаёт структурированный PASS/FAIL. Не исправляет | Sonnet 5.5, medium |
| **Asset agent** | Подбирает или генерирует графику и звук по списку из GDD | зависит от стратегии |
| **Release writer** | Название, описания, теги, скриншоты, иконка. Геймплей не трогает | Sonnet 5.5, low |
| **Final gate** | Детерминированный чеклист плюс краткое LLM-заключение READY/FAILED | Haiku 4.5 / Sonnet 5.5 |
| **Escalation** | Сложная отладка, когда Engineer застрял | Opus 5.5, high |

\* Значения предварительные и будут уточнены на этапе исследования. Модели задаются только в конфиге.

## State machine

```text
CREATED
  ↓
SPEC            Planner: GDD + критерии приёмки
  ↓
PLAN            Planner: архитектура + список задач
  ↓
PROTOTYPE       Engineer: минимальный играбельный цикл + web-сборка
  ↓
VERIFY ⇄ FIX    проверки → Evaluator → Engineer (до N итераций)
  ↓
HUMAN_REVIEW    человек: продолжить / переделать / стоп (опционально)
  ↓
BUILD           цикл по задачам: IMPLEMENT → VERIFY → EVALUATE → FIX
  ↓
ASSETS          замена заглушек на ассеты
  ↓
YANDEX_AUDIT    валидаторы + SDK-проверки → FIX
  ↓
RELEASE_PREP    метаданные, скриншоты, иконка, пакет
  ↓
FINAL_GATE
  ↓
READY / FAILED
```

Из любого состояния возможен переход в служебные: **ESCALATED** (подключение Opus), **BLOCKED** (нужен человек), **ROLLED_BACK** (откат к чекпоинту). После каждого успешного этапа создаётся Git-тег-чекпоинт.

## Инфраструктура проверки игры

Это ядро, которое нужно спроектировать особенно тщательно.

- **Шаблон игры** с autoload `HarnessDebug`:
  - дамп состояния игры в JSON (позиция игрока, сцена, счёт, флаги);
  - скриптованный ввод (нажатия по таймлайну);
  - команды (телепорт, пропуск уровня, вызов события);
  - запись ошибок и предупреждений в файл.
- **Python test runner**, который запускает Godot со сценарием и проверяет утверждения:
  - smoke: проект открывается, главная сцена грузится, ошибок нет;
  - сценарии: «вправо 3 с → x увеличился, игрок жив»;
  - проходимость: уровень можно пройти скриптом.
- **Скриншоты и видео** через Xvfb на Linux (в `--headless` рендеринга нет).
- **Web-проверка** через Playwright: билд грузится в Chromium, нет ошибок в консоли, есть скриншот, работает тач-ввод в мобильной эмуляции.
- Engineer обязан писать сценарии для новых механик. Evaluator проверяет, что они есть и проходят.

## Структура рабочей папки

```text
workspace/
  game_001/
    repo/              Git-репозиторий игры (Godot-проект)
    harness/
      events.jsonl     журнал событий (append-only) — источник истины
      state.json       текущее состояние, восстанавливается из журнала
      artifacts/       GDD, архитектура, план задач
      reports/         отчёты проверок и Evaluator, скриншоты, видео
      runs/            транскрипты Claude Code, логи по запускам
```

## Этапы разработки

**Этап 0. Окружение**
Python + uv, Git, Godot 4.x с export templates, Xvfb (Linux), Node.js + Playwright, ffmpeg.
*Готово, когда* проходит команда проверки окружения `harness doctor`.

**Этап 1. Исследование и ARCHITECTURE.md**
Godogen, GameForge-Harness, godot-gamestudio и другие проекты; документация Claude Code (headless-режим против Agent SDK, права, вывод стоимости); модели и их стоимость; официальная документация Yandex Games; ограничения Web-экспорта Godot (версия, однопоточный режим, размер сборки, JavaScriptBridge).
*Готово, когда* ARCHITECTURE.md одобрен пользователем. Без этого код не пишется.

**Этап 2. Скелет (MVP-0)**
CLI `create / run / status`, ClaudeCodeRunner, журнал событий, Git-чекпоинт. Один агент — Engineer — получает идею и создаёт проект из шаблона.
*Готово, когда* `harness create "simple 2D platformer"` и `harness run game_001` дают Godot-проект, который открывается без ошибок, с чекпоинтом и записанным состоянием.

**Этап 3. Проверка игры (MVP-1)**
Шаблон с HarnessDebug, test runner, smoke-тесты, сценарии, скриншоты.
*Готово, когда* `harness test game_001` выдаёт отчёт с результатами сценариев и скриншотами.

**Этап 4. Web-сборка**
Экспорт в Web, Playwright-проверка, мобильная эмуляция.
*Готово, когда* прототип собирается и запускается в браузере без ошибок консоли.

**Этап 5. Цикл Planner → Engineer ⇄ Evaluator**
Planner, Evaluator со структурированным выводом, цикл исправлений, лимиты итераций, бюджеты, эскалация на Opus, circuit breaker, `resume`, `rollback`.
*Готово, когда* система сама доводит простую игру до PASS или корректно останавливается с причиной, а после прерывания процесса продолжает с того же места.

**Этап 6. Решение человека и ассеты**
Гейт после прототипа. Стратегия ассетов (CC0-библиотеки, процедурная графика, генерация) — выбирается по итогам исследования.
*Готово, когда* игра проходит путь без серых прямоугольников, а гейт можно включить или выключить.

**Этап 7. Yandex-слой**
Требования в YAML со ссылками на источники, мост к SDK через JavaScriptBridge, валидаторы, проверка рекламы и сохранений.
*Готово, когда* `harness audit game_001` выдаёт отчёт по каждому требованию: пройдено, не пройдено или нужна ручная проверка.

**Этап 8. Релиз и финальный гейт**
Release writer, пакет для загрузки, Final gate.
*Готово, когда* `harness release game_001` выдаёт архив и метаданные, а Final gate — READY или FAILED с причинами.

**Этап 9. Укрепление и open-source**
Docker-изоляция проектов, тесты восстановления (обрыв процесса, сбой Godot, кривой JSON), README, LICENSE, CONTRIBUTING, `.env.example`.

## CLI

```bash
harness doctor                 # проверка окружения
harness create "<идея>"        # создать проект
harness run game_001           # запустить или продолжить пайплайн
harness resume game_001        # продолжить после сбоя
harness status game_001        # текущее состояние, итерации, бюджет
harness test game_001          # только проверки, без агентов
harness audit game_001         # Yandex-аудит
harness approve game_001       # решение на HUMAN_REVIEW
harness rollback game_001 --to prototype-complete
harness release game_001
harness logs game_001 [--agent engineer]
```

## Ограничители

- лимит итераций на цикл VERIFY ⇄ FIX и на задачу;
- лимит стоимости на проект и на этап;
- таймаут на каждый запуск агента;
- эскалация: N неудачных итераций → Opus → ещё M итераций → BLOCKED;
- circuit breaker: одна и та же ошибка K раз подряд → остановка с отчётом.
